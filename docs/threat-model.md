# 脅威モデル

## 前提

stream-buddy は配信者の PC の中だけで動き、外部に公開するサーバーを持たない。
そのため、守るべき入り口は次の3つに絞られる。

1. **PC 内で動くローカルサーバー**（WebSocket とページ配信）
2. **公開リポジトリと配布物**（コード、exe、依存ライブラリ）
3. **ユーザーの PC 上のファイル**（設定、ログ、音声認識モデル）

## 守るもの

| 資産 | 漏れる・壊れると何が起きるか |
| --- | --- |
| 配信者の音声・発話内容 | プライバシーの侵害（音声と認識した文字列は、メモリ上で扱って捨てる。requirements.md の「プライバシー」） |
| 配信画面の表示内容 | 配信中に不適切な内容を表示させられる |
| PC 上のファイル | 意図しない場所への書き込み |
| 作者の個人情報・秘密情報 | 公開リポジトリからの流出 |
| 配布物の信頼性 | 改ざんされた exe を使わされる |

## 信頼の境界

```
[ インターネット ]  ×  外部への通信なし
        │
[ ブラウザで開いた任意のサイト ] ── ローカルの WebSocket に接続を試みる可能性（境界 A）
        │
[ 127.0.0.1 の stream-buddy サーバー ]
        │
[ OBS のブラウザソース（正規のページ） ]
```

境界 A が最も重要。ブラウザは、どのサイトからでも `ws://127.0.0.1:...` への接続を試みることができる。

また、悪意あるサイトは自分のドメイン名の DNS を書き換えて `127.0.0.1` を指させることができる（DNS リバインディング）。
この場合、ブラウザからは「同じサイトへのリクエスト」に見えるため、Origin の確認だけではページの取得などを防げない。
そこでサーバーは、すべての HTTP リクエストと WebSocket 接続で `Host` ヘッダーが `127.0.0.1:<port>` と一致することを確認する。違えば、HTTP には 400 を返し、WebSocket は受け入れずに閉じる。

## 脅威と対策

| ID | 脅威 | 対策 | 残るリスク |
| --- | --- | --- | --- |
| SR-01 | LAN の他機器からの接続 | `127.0.0.1` のみで待ち受け | なし |
| SR-02 | 悪意あるサイトからの WebSocket 接続 | Origin 確認＋トークン。トークンは初回に作って `%LOCALAPPDATA%\stream-buddy\token` に保存し、使い回す。`--reset-token` で作り直せる（ADR 0002） | トークン入りの URL が配信に映ると漏れ、作り直すまで有効 → 起動時のコンソールと README で「URL や開発者ツールの画面を配信に映さない」「映ってしまったら `--reset-token` で作り直す」と案内する |
| SR-02 | DNS リバインディング（悪意あるドメインを `127.0.0.1` に向けて、ページや WebSocket に届く） | `Host` ヘッダーが `127.0.0.1:<port>` と一致しなければ拒否（HTTP は 400、WebSocket は受け入れずに閉じる）。あわせてトークンも必要 | なし |
| SR-03 | 想定外のメッセージ | スキーマ検証して破棄 | なし |
| SR-04 | 表示文字によるスクリプト実行 | `textContent`、CSP | なし |
| SR-05 | キーロガー化・その疑い | `RegisterHotKey` で設定した 2 つのキー（の組み合わせ）だけを登録して受け取る。`user32` で呼ぶのは `RegisterHotKey`・`UnregisterHotKey`・`GetMessageW`・`PostThreadMessageW` だけ。キーボードのフック（`SetWindowsHookEx`）、キーの状態を調べる API（`GetAsyncKeyState`・`GetKeyState`・`GetKeyboardState`）、生の入力（`RegisterRawInputDevices`）、キーボード関係のライブラリ（`keyboard`・`pynput`・`pywin32` など）は使わない（テストで検査する） | 登録中はそのキーがほかのアプリに届かない → README と設定例で、ゲームと重なるときは修飾キーとの組み合わせに変えるよう案内する |
| SR-06 | ログ出力先の悪用 | 設定した `output_dir` の中にだけ書く。書き込み先を正規化し、`output_dir` の中に収まることを確認してから書く | なし |
| SR-07 | モデルファイルの改ざん | 公式配布元から人が取得する（自動ダウンロードしない）。全ファイルの SHA-256 の一覧（`src/stream_buddy/data/vosk-model-small-ja-0.22.sha256`）を同梱し、読み込む前に照合する。ファイルがない・ハッシュが違う・一覧にないファイルがあれば読み込まずに起動しない。`--check-model` で照合だけを行える | 配布元自体の侵害。照合のあと読み込むまでの間の書き換え（ローカルで同じ権限を持つ攻撃者のみ） |
| SR-08 | 依存の脆弱性 | ロック、Dependabot、pip-audit。本体の依存の `vosk` は `requests`（と `tqdm`・`srt` など）を連れてくる。`vosk` はモデルの自動ダウンロードのために `requests` を使うが、stream-buddy はその関数を呼ばず、モデルのフォルダを必ず渡すため、通信は発生しない。`requests` などの連れてくる依存も `pip-audit` の対象 | 未公表の脆弱性 |
| SR-09 | 秘密情報の流出 | 秘密情報を持たない設計、gitleaks、プッシュ保護 | なし |
| SR-10 | CI の悪用 | ハッシュ固定、最小権限 | なし |
| SR-11 | exe の改ざん・偽物 | CI ビルド、attestation、SHA-256 | 利用者が確認しない場合 → README で手順を案内 |

## AI 開発に関する対策

実装の多くを AI エージェントが行うため、次の多重の守りを置く。

1. **コミット時**：pre-commit（gitleaks、秘密鍵検知、ruff）
2. **AI の権限**：`.claude/settings.json` で push・フック回避・守りの設定ファイルの編集を禁止
3. **push は人間**：差分を確認してから push する
4. **GitHub 側**：プッシュ保護、ブランチ保護、CI が通らないとマージできない
